# XIOM -- Live Patching & Hot-Swap Architecture (v0.61)

**Version:** Design Spec v1.0 | **Target:** Post-Selfhost + Post-Scale (v0.61)
**Status:** DESIGN ONLY -- implementation begins after v0.60 (Scaling stable).
**Branch (future):** `feat/architect/live-patching`
**Owner:** Compiler + Runtime Team
**Source:** Pre-selfhost design review (2026-08-10); supersedes earlier hot-reload-only plans.

---

## 0. Executive Summary

XIOM already has **JIT Compilation**, **JIT Caching**, **Hot Reload**, and **Watch
Mode**. This plan upgrades that foundation to **Production Live Patching**:

> The ability to inject new, verified machine code into a running XIOM process,
> without restarting the process, without dropping network connections, and with
> automatic rollback if the new code violates its contracts or crashes.

| Requirement | What it delivers |
|-------------|------------------|
| Zero-Downtime Swap | Function pointers swapped atomically at safe execution points. No process restart. |
| State Preservation | Heap data (structs, globals) remains intact. New code operates on live state. |
| AI-Generated Code Ready | JIT compiles code generated by an onboard LLM, runs it through Z3 verification, and atomically promotes it. |
| Automatic Rollback | If patched code violates `ensures` or panics in the first 100 ms, the runtime reverts to the previous version. |
| Space-Grade Safety | Fully compatible with the Unsafe Confinement architecture (fault traps catch hardware errors during the patch). |

## 1. Core Architecture

### 1.1 The Function Pointer Table (the "Dispatch Vector")

Every public function eligible for hot-patching is called via a global, versioned
function pointer table (like a C++ vtable, but globally accessible) instead of a
direct branch.

```c
// In the XIOM runtime (CRT)
typedef struct {
    void* fn_ptr;           // Current machine code address
    uint64_t version;       // Incremented on each patch
    char* name;             // "math::sqrt"
    uint64_t contract_hash; // Hash of the requires/ensures
} XiomPatchSlot;

// Global array (read-only, except when swapping)
extern XiomPatchSlot XIOM_PATCH_TABLE[];
```

**Compiler codegen** -- for a function marked `#[patchable]`:

```xiom
#[patchable]
pub fn sqrt(x: Float64) -> Float64
  requires: x >= 0.0
{
    // The compiler does NOT generate a direct branch to sqrt.
    // It generates:
    //   call [XIOM_PATCH_TABLE + offset]
    // The runtime resolves the pointer at runtime.
}
```

**Performance:** a table lookup is a single `jmp *table` (~1 cycle slower than a
direct call) -- zero measurable impact.

### 1.2 The JIT Pipeline (the "Patch Factory")

When the AI (or the developer) submits a new version of `sqrt`:

1. **Source Ingest:** the runtime receives a string containing the new source.
2. **Compilation:** the runtime spins up the XIOM JIT compiler (same backend as
   `xiom run`). LLVM IR -> native machine code. It does NOT link into the main
   binary yet -- it allocates a new executable memory page
   (`PAGE_EXECUTE_READWRITE` / `mmap PROT_EXEC`) and writes the code there.
3. **Sandbox Verification:** the JIT executes the new code in a sandbox using the
   Unsafe Confinement traps (v0.57), feeds it a read-only copy of current live
   data, and checks that `ensures` clauses hold. If the code faults or fails the
   contract, the patch is rejected immediately.

### 1.3 The Atomic Swap (the "Hot Swap")

If the sandbox passes:

1. **Quiescent State:** the runtime waits for all threads to reach a safe point
   (end of the current main loop, or a yield/await boundary). Pauses all threads
   briefly (~50 us).
2. **Pointer Swap:** atomic compare-and-swap (CAS) on
   `XIOM_PATCH_TABLE[slot].fn_ptr` -> new machine code.
3. **Version Bump:** increment `version`.
4. **Resume:** all threads resume. Every subsequent call executes the new code.

## 2. Implementation Phases

| Phase | Scope | Where | Effort |
|-------|-------|-------|--------|
| **1. Patchable Function ABI** | `#[patchable]` parser attribute; codegen emits calls via `XIOM_PATCH_TABLE` instead of direct calls for marked fns. | Compiler (parser + codegen) | ~1 week |
| **2. JIT Sandbox** | `xiom_jit_patch(source, fn_name)` in CRT. Reuse existing JIT pipeline; compile patch into a new memory page; run against a snapshot of the current heap; check `ensures`; ensure it doesn't trip the unsafe trap. | Runtime (CRT + xiom-jit) | ~2 weeks |
| **3. Atomic Swapper** | `xiom_swap_function(name, new_ptr)`. Global rwlock/spinlock only during the swap (O(1), <1 ms). Version tracking (store old pointer + version). | Runtime (CRT) | ~1 week |
| **4. Automatic Rollback** | After applying a patch, a Stabilization Timer (100 ms) runs. Every call increments a counter; a contract violation / Err / fault triggers swapping the old pointer back. | Runtime + contracts | ~1 week |
| **5. AI Integration / Watch Mode** | `--patch` and `--watch-patch` flags on `xiom run`. Watch source; on save, JIT-compile the delta and apply to the running process. | CLI | ~1 week |

### Phase 2 detail (JIT sandbox)

Reuse:
- `JitEngine::compile_module(source)` -> `.dll` (already works).
- `JitModule::get_function_ptr(name)` (exposure change -- see OrcJIT_PLAN S7).
- Unsafe Confinement traps (`xiom_trampoline_call`, guard arena) for isolation.

### Phase 4 detail (rollback triggers)

| Trigger | Action |
|---------|--------|
| Patch fails compilation | JIT returns error string; caller (AI) retries; process never stops. |
| Patch compiles but violates `requires` | Sandbox detects; patch rejected; log `"Contract violation: requires x > 0"`. |
| Patch compiles but crashes (SIGSEGV) | Unsafe confinement trap catches it; JIT returns `Err(HardwareFault)`; patch rejected; process stays alive. |
| Patch applied but hangs (>50 ms) | Watchdog timer aborts the thread and rolls back the pointer. |
| Rollback pointer corrupt | Runtime panics that thread only; main process keeps running. |

## 3. The "Black Box" Integration (Spacecraft Scenario)

1. Onboard AI detects navigation drift.
2. AI writes a new `pid_controller.xi` function.
3. AI sends source to the JIT Sandbox (Phase 2).
4. Sandbox runs the new function against the last 5 s of telemetry; math checks out.
5. Runtime performs the Atomic Swap (Phase 3).
6. Spacecraft corrects its trajectory.
7. Safety net: if the new controller causes a contract violation (e.g., overshoot),
   Phase 4 detects it in 100 ms, rolls back, logs `"Patch rejected, reverting to
   safe trajectory."`

---

## 4. Error Handling & Edge Cases

| Failure Mode | Mitigation |
|--------------|-----------|
| Patch fails compilation (syntax error) | JIT returns error string; caller retries; process never stops. |
| Patch violates `requires` | Sandbox execution detects; patch rejected; logs contract violation. |
| Patch crashes (SIGSEGV) | Unsafe confinement trap catches it; `Err(HardwareFault)`; patch rejected; process stays alive. |
| Patch hangs (infinite loop) | Per-function watchdog timer (>50 ms) aborts the thread and rolls back the pointer. |
| Rollback failure | Corrupt rollback pointer -> panic that thread only; main process keeps running. |

## 5. Success Criteria (for the Agent)

- [ ] `#[patchable]` attribute compiles to a table lookup instead of a direct branch.
- [ ] `xiom run --patch my_server.xi` replaces a function in the running process without a restart.
- [ ] A contract violation in patched code triggers automatic rollback to the previous version.
- [ ] A SIGSEGV in patched code is caught by the unsafe trap (v0.57) and does not crash the process.
- [ ] The JIT cache stores the compiled patch so a process restart (OS update) loads the latest patched version directly.

## 6. Why This Is Future-Proof

| Threat | How XIOM handles it |
|--------|---------------------|
| AI writes bad code | JIT Sandbox + Z3 contracts block bad logic before it touches the live system. |
| AI writes crashing code | Unsafe Confinement + SIGSEGV traps block hardware faults. |
| Hardware failure during patch | SIGBUS during code memcpy -> runtime retries the patch on a new physical memory slot. |
| Malicious patch | Contract system confines raw pointers; unsafe blocks enforce memory ownership. |

**Implementation note:** the JIT Pipeline (Phase 2) uses the exact same LLVM
backend as `xiom build` -- no divergence between "compiled at build time" and
"compiled at runtime". This guarantees ABI stability and eliminates runtime vs
compile-time inconsistency.

## 7. Dependencies & Start Condition

- **Start condition:** v0.60 (Scaling) must be stable. Live Patching extends the
  scaling architecture -- the file-watching + dependency-graph intelligence from
  Scaling knows which functions changed so only those are patched.
- **CTFE:** contract pre-simplification (Integration A in CTFE_PLAN) applies
  here -- `requires` checks in the sandbox may be CTFE-reduced when arguments are
  constant.
- **OrcJIT:** `JitModule::get_function_ptr()` exposure (OrcJIT_PLAN S7) is the
  only prerequisite JIT work.
