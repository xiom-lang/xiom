## P0 -- correctness (no candidate before these)

### Nested enum/pattern payloads (1615/1645/1243/1451/1550 family)

- [x] `stmt.rs`: arm check for `Some(inner)`/`Ok(inner)`/`Err(inner)`
      recurses when `inner` is `Pattern::Variant`: load the inner enum
      payload, check its discriminant, and branch only on a match.
- [x] `stmt.rs` binding: `bind_variant_payload_fields` +
      `enum_payload_value_ptr` bind Float64/Float32/Str/Vec/struct fields,
      with `local_xiom_types`, `local_boxed_struct`, and
      `local_vec_handle` tracking.
- [x] Cover `Some(Num(f64))`, `Result[Inner, Str]` `Ok(Num(f64))`,
      nested `Text(Str)`, and `Some(JsonValue.Number(f64))` in debug and
      release-shaped probes.
- [x] Regression fixture + e2e lock `m1615_nested_enum_payloads`
      (exact values, JSON included).
- [x] No regression for top-level `Pattern::Variant`, borrowed enum
      matches (1731), or boxed Str payloads (2045).
- [x] 1645: direct `Err(E.Bad("..."))` pushed into `Vec[Result[Str, E]]`
      keeps the Str. Root cause: the direct ctor was lowered against the
      ERASED `%struct.Result` (24 B) while the receiver Vec's declared
      element is the concrete monomorph (32 B); the push memcpy'd the
      concrete size over the erased value and clobbered the Vec stride.
      `Vec.push` now rebuilds an erased Result/Option into the concrete
      element layout and sizes the element from the DECLARED type.
      e2e `e2e_m1827_err_str_vec_push`.

### Safe generic substitution (m372/1451/1550)

- [x] Bisect artifact confirmed: `d04cd3265` explicit type-arg
      substitution breaks m372; reverting it breaks m1520.
- [x] Generic pointee base canonicalization (`Pair[Int]` -> `Pair`) plus
      the LLVM pointer fallback and pointer-local inference; the receiver
      shortcut no longer preempts `ptr.read`/`ptr.write`.
- [x] Keep `_max_via[U]` -> `_max_via_Int` and the
      `EnumerateIter[Int].map` e2e chain green; m372 is 42/42.
- [x] e2e locks for m372/m1520/m1550 are green.
- [x] True tuple-returning `p_iter_enumerate_tuple` (`em[1].0`) is green.
      `EnumerateIter.map` binds U to `Tuple__Int__Int` from the callback
      return, and the outer `collect` resolves the map call's returned
      `MapIter[(Int, Int), U]` on demand (before the inner call emits).
      `MapIter.collect_Tuple__Int__Int_Tuple__Int__Int` reads 16-byte
      elements; e2e `e2e_m1550_enumerate_tuple_map_true` locks
      `em=[(0,10),(1,12),(2,14)]`, including `em[1].0 == 1`. The old
      `Vec[Int]` binding that lowered `em[i].0` to a literal 0 is fixed by
      the same on-demand return substitution.
      Fixed in `infer_call_return_xiom_on_demand` + the callback-return
      canonicalization in `infer_generic_arg_from_container` /
      `fn_arg_generic_binding` / `wrap_fn_ref_env`.
- [ ] Add a unit test for the substitution guard.

### 1827 data-loss cluster (1645/2045/openblas/http)

- [x] Direct `Err(E.Bad("direct"))` pushed into `Vec[Result[Str, E]]`
      keeps the payload (see 1645 above). Probe:
      `packages/xiom.jev/docs/repro/batch_result_vec_push.xi`;
      e2e `e2e_m1827_err_str_vec_push`.
- [x] Cross-module `Result[(NominalType, Vec[Int]), Str]` keeps the Vec
      contents (len=2, 11/22). Root cause: the tuple literal's canonical
      name (`Tuple__Handle__Vec`) was registered, then `struct_ty` was
      re-inferred and fell back to the enclosing fn's `%struct.Result`;
      the Vec element was coerced to its data pointer and len/cap/elem_size
      were dropped. The literal now uses its registered canonical struct
      directly, and tuple element naming consults `local_xiom_types`.
      Probes: `packages/xiom-openblas/tests/probe_vec_in_tuple_{lib,main}.xi`;
      e2e `e2e_m1827_vec_in_tuple_cross_module`.
- [x] Direct `Err(Enum.Variant(..))` match descends into the inner enum.
      Root cause: a single-letter enum name (`E`) was filtered by the
      generic-placeholder heuristic in `scrutinee_payload_xiom`, so the
      inner discriminant check was omitted and no Err arm ran. Registered
      types now win over the placeholder heuristic.
      Probe: `packages/xiom-http/docs/probe_match_result_enum_defect.xi`;
      e2e `e2e_m1827_match_err_enum`.
- [x] All three probes are in the regression/e2e set
      (`m1827_err_str_vec_push.xi`, `m1827_match_err_enum.xi`,
      `m1827_vec_in_tuple_{lib,main}.xi`). Release-mode gating lands with
      the `XIOM_TEST_COMPILER` harness switch in the release-parity job.

### 1529 stored-fn pointer spelling (LLVM 14 / Apple arm64)

- [x] Replaced `ptrtoint ptr @__unsafe_block_N` with a typed
      `ptrtoint i64 (i8*)* @__unsafe_block_N` so clang 14 and Apple arm64
      accept the IR. The same fix covers the four closure/block thunk env
      sites (`__closure_N`): each now emits its real function-pointer type
      instead of the opaque `ptr` spelling.
- [x] IR grep locks: `e2e_m1529_ir_typed_ptrtoint_{x64,arm}` and
      `e2e_m1529_stored_fn_value_arm_ir` assert `ptrtoint ptr` is absent
      from `--target arm` IR for the unsafe-block and stored-fn fixtures
      (`m1703_fn_value_vec_tuple.xi` runtime re-checked).
- [x] Run the stored-fn probe through the arm64 floor job: `arm64-floor`
      (`ubuntu-22.04-arm`, clang 14) builds the release compiler and runs
      `e2e_m1529` + `e2e_m1550` + `e2e_m1827`. Locally verified via
      `--target arm` IR spelling.
